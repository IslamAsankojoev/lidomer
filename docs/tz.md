# ТЗ: Отчёт для маркетинга — поэтапная реализация для ИИ

Nov 16, 2026 · @Islam

## Как читать ТЗ

Каждая задача помечена: кто её делает и насколько она критична. Редактор документа красит фон ячеек, а не буквы, поэтому цвет стоит на строке таблицы, а метка в первой колонке дублирует его — так ИИ-агент поймёт разметку и в Markdown-выгрузке.

| Метка | Цвет | Что значит |
| --- | --- | --- |
| **ИИ** | без цвета | Делает ИИ-агент сам: код, миграции, тесты, деплой через CI |
| **Человек** | зелёный | Делает владелец или маркетолог руками: доступы, ключи, настройки в кабинетах Meta, Ward, Bitrix24, Telegram. У ИИ туда доступа нет |
| **Важно** | оранжевый | Правило или ограничение, которое нельзя нарушать; ИИ не реализует его отдельно, а соблюдает везде |
| **Изучить** | синий | Новое предложение или то, что не додумано: проверить до начала этапа и принять решение |

**Как ИИ-агенту работать с ТЗ:** брать этапы строго по порядку; этап закрыт, только когда выполнены все пункты «Готово, когда»; задачи «Человек» не делать и не обходить — остановиться и попросить владельца; по задачам «Изучить» сначала принести вывод, потом писать код.

## Цель и рамки первой версии

Первая версия — кабинет для одной компании: сводит Meta Ads, Ward bot и Bitrix24 в точный отчёт и отправляет его в Telegram по расписанию. Продуктовое описание экранов и формул — в документе [«Отчёт для маркетинга — описание проекта и интерфейса»](https://claude.ai/artifact/E84UbpGu5JNTy3U13GnaDX); это ТЗ опирается на него.

**Решения, принятые по открытым вопросам:**

| Метка | Решение | Что это значит для кода |
| --- | --- | --- |
| Важно | На старте один бизнес, потом SaaS | Во всех таблицах с первого дня есть `workspace_id`, доступ всегда проверяется по нему. Регистрации новых компаний и оплаты пока нет |
| ИИ | Отчёты только в Telegram | Канал отправки — адаптер с общим интерфейсом; реализуем только Telegram |
| Важно | Хостинг — Vercel и Supabase, картинки в Supabase Storage | Нет постоянно работающих процессов и Redis: фоновая работа запускается по расписанию и делится на короткие задачи |
| Важно | Валюта — как в Meta, под ней мелко «≈ … сом» | Сумма в валюте кабинета главная; сомы — справочно, по курсу на дату расхода, всегда со знаком ≈ |
| ИИ | Часовой пояс и валюту кабинета узнаём через API | Читать поля `timezone_name` и `currency` рекламного аккаунта; если пояс не Asia/Bishkek — показывать предупреждение |
| ИИ | Роли — как в описании проекта | Владелец, Маркетолог, Продажи, Наблюдатель; владелец бизнеса смотрит метрики сам |
| Изучить | В Bitrix24 лиды приходят и от Ward, и напрямую от таргета | Выяснить канал (лид-формы Meta или другое) и есть ли у таких сделок UTM: от этого зависит «лиды с рекламы · факт» |
| Изучить | Лиды из Direct Ward отдаёт без пометки рекламы (70 из 182 за 9–16 ноября) | Пока не относить их к органике молча: отдельная группа «Direct, источник не определён», пока не станет известно, есть ли кампании на переписку |

**Входит в первую версию:** экраны «Обзор», «Креативы», «Лиды», «Отчёты», «Интеграции», «Настройки»; синхронизация Meta, Ward и Bitrix24; сверка и метрики; отчёты по расписанию в Telegram; алерт о сбое интеграции.

**Не входит:** полный экран «Сверка» с ручным разбором, ROMI и план, алерты по метрикам, команды бота, WhatsApp, регистрация других компаний. Это раздел «После запуска».

## Сервисы и стек

Два сервиса на Vercel — фронтенд на Next.js и бэкенд на NestJS — и Supabase для базы, входа, файлов, расписания и очередей. Redis и BullMQ из описания проекта убираем: на Vercel нет постоянно работающих процессов, а Supabase умеет запускать задачи по расписанию и держать очередь прямо в Postgres.

&#91;embedded content: сервисы · 2 приложения на Vercel, Supabase, внешние API\]

Всё, что читает данные или ходит во внешние API, живёт в api; web только показывает и рисует картинку отчёта.

| Сервис | Где работает | Отвечает за |
| --- | --- | --- |
| `apps/web` — Next.js | Vercel | Кабинет, вход, графики, таблицы; картинка отчёта (маршрут `/api/og/report`) |
| `apps/api` — NestJS | Vercel: всё приложение — одна функция на Fluid compute | Интеграции, синхронизация, сверка, метрики, отчёты, вебхук Telegram, задачи по расписанию |
| Supabase | Облако Supabase | Postgres, Auth, Storage (превью и картинки отчётов), Cron (`pg_cron` + `pg_net`), Queues (`pgmq`) |
| Внешние API | — | Meta Marketing API, Ward API, Bitrix24 REST, Telegram Bot API |

**Как идёт фоновая работа:** Supabase Cron по расписанию вызывает защищённый эндпоинт `POST /jobs/tick` в api. Тот кладёт задачи в очередь («синхронизировать Ward за день», «отправить отчёт») и разбирает их небольшими порциями, укладываясь в лимит времени функции; что не успело — остаётся в очереди до следующего запуска.

## Репозиторий и правила для ИИ-агента

Один монорепозиторий, два приложения и три общих пакета. Это ТЗ кладётся в `docs/` как Markdown, а правила ниже — в `AGENTS.md` в корне, чтобы агент читал их в каждой сессии.

```
/
├─ apps/
│  ├─ web/          Next.js — кабинет
│  └─ api/          NestJS — бэкенд
│     └─ src/modules/
│        auth, workspaces, integrations/{meta-ads,ward,bitrix24},
│        sync, reconciliation, metrics, reports,
│        delivery/telegram, alerts, audit, jobs
├─ packages/
│  ├─ shared/       zod-схемы, типы, формулы, форматтеры
│  ├─ db/           схема Drizzle, миграции, сиды
│  └─ config/       tsconfig, eslint, prettier
├─ supabase/        SQL для cron, очередей и Storage
├─ docs/            ТЗ, решения (decisions/*.md)
└─ AGENTS.md        правила для ИИ-агента
```

| Метка | Правило |
| --- | --- |
| Важно | Коммиты — только от имени владельца репозитория, без строк соавторства ИИ (`Co-Authored-By`) |
| Важно | Секреты никогда не попадают в код, git и чат: только переменные окружения Vercel и Supabase. В репозитории — только `.env.example` без значений |
| Важно | Внешние системы только читаем: в Meta, Ward и Bitrix24 ничего не создаём и не меняем. Единственная запись наружу — сообщения в Telegram |
| Важно | Никаких выдуманных данных: если источник не ответил — «нет данных», а не ноль. Фейковые данные — только в тестах и сидах, и они помечены |
| ИИ | Каждый этап — отдельная ветка и pull request. В начале PR — короткий план, в конце — отмеченный чек-лист «Готово, когда» |
| ИИ | CI в GitHub Actions: линтер, проверка типов, тесты. В `main` — только с зелёным CI |
| ИИ | Тесты обязательны для формул, сверки, часовых поясов и клиентов внешних API |
| ИИ | Схема базы меняется только миграциями Drizzle |
| ИИ | Спорное техническое решение записывается в `docs/decisions/` одним файлом: контекст, решение, последствия |
| Человек | Выдаёт агенту доступ к репозиторию, вносит секреты в Vercel и Supabase, принимает и сливает PR |

## Модель данных

Данные лежат в три слоя: сырые ответы API → таблицы источников → сверенный журнал лидов и метрики. Во всех таблицах, кроме справочных, есть `workspace_id`; названия колонок ИИ уточняет по реальным ответам API на этапе 2.

| Метка | Таблица | Что хранит |
| --- | --- | --- |
| ИИ | `workspaces`, `members` | Компания (название, логотип, часовой пояс, валюта показа) и её пользователи из Supabase Auth с ролями |
| ИИ | `integrations` | Подключения: тип (`meta_ads`, `ward`, `bitrix24`, `telegram`), имя, статус, зашифрованные секреты, настройки, время и ошибка последней синхронизации |
| ИИ | `sync_runs` | Каждый запуск синхронизации: источник, период, статус, число записей, ошибка |
| Важно | `raw_payloads` | Ответ внешнего API как есть, с запросом и временем. Только добавление, никогда не меняется: это доказательство и основа для пересчёта |
| ИИ | `meta_ad_accounts` | Рекламные аккаунты: id, название, `currency`, `timezone_name`, статус |
| ИИ | `meta_campaigns`, `meta_adsets`, `meta_ads` | Структура рекламы; у объявления — название, статус, id креатива и путь к копии превью в Storage |
| ИИ | `meta_insights_daily` | Объявление × день: расход в минимальных единицах, показы, клики, `actions` целиком; уникально по (объявление, день) |
| ИИ | `ward_conversations` | Диалоги Ward: канал (комментарий, Direct, запрос), объявление, пост, кто отвечает, есть ли лид, время |
| ИИ | `ward_leads` | Лиды Ward: время, имя, телефон, Instagram, источник (текст), статус, сумма, сущность и id в CRM, объявление, пост, анкета `facts` |
| ИИ | `b24_deals`, `b24_stage_map` | Сделки Bitrix24 (стадия, направление, сумма, источник, UTM, ответственный, даты) и соответствие стадий статусам «в работе», «продажа», «отказ» |
| ИИ | `leads` | Единый журнал после сверки: ключ человека (Instagram или телефон), канал, объявление, ссылки на лид Ward и сделку, статус, сумма, повторный ли, флаги проблем |
| Важно | `lead_overrides`, `audit_log` | Ручные правки и действия: что было, что стало, кто, когда, почему. Исходные данные правки не трогают |
| ИИ | `metrics_daily` | Агрегаты по дню и объявлению: расход, лиды (факт и Meta), органика, с телефоном, продажи. Всегда пересчитываемы из таблиц выше |
| ИИ | `fx_rates` | Курс валюты кабинета к сому по дням и источник курса |
| ИИ | `reports`, `report_recipients`, `report_runs` | Отчёты, получатели (группа и тема Telegram), запуски со снимком цифр, путём к картинке и статусом доставки |
| ИИ | `telegram_chats` | Группы, в которые добавлен бот |

## Этап 0 — подготовка

Этот этап почти целиком делает человек: ИИ не может создать аккаунты и выдать себе доступы. Без него этапы 1–2 не начинаются.

| Метка | Задача | Где |
| --- | --- | --- |
| Человек | Создать репозиторий и дать доступ ИИ-агенту | GitHub |
| Человек | Создать два проекта Supabase: dev и prod. Включить Cron и Queues | Supabase |
| Человек | Создать два проекта Vercel из одного репозитория: `web` (корень `apps/web`) и `api` (корень `apps/api`) | Vercel |
| Изучить | Регионы: Supabase и функции Vercel должны стоять в одном регионе, ближайшем к Бишкеку | Supabase, Vercel |
| Изучить | Тариф Vercel: проверить, можно ли коммерческий проект и будущий SaaS держать на Hobby, и лимиты длительности функций на выбранном тарифе | Vercel |
| Человек | Meta: создать приложение типа Business, добавить Marketing API и Facebook Login for Business, создать конфигурацию входа с токеном системного пользователя и правом `ads_read` | developers.facebook.com |
| Человек | В бизнес-портфолио дать приложению и системному пользователю доступ к рекламному аккаунту на чтение | Meta Business Suite |
| Изучить | Какой уровень доступа к Marketing API нужен для своего кабинета и потом для чужих (SaaS), нужна ли проверка приложения и бизнеса | Meta |
| Человек | Ward: ключ для отчётов уже создан в «Подключения → API для отчётов»; внести его в кабинет через экран «Интеграции» после этапа 2 | Ward |
| Человек | Написать в поддержку Ward три просьбы: отдавать `conversation_id` и структурный источник в публичном API; сохранять рекламную метку для Direct; добавить вебхук о новом лиде | Ward |
| Человек | Bitrix24: создать отдельный входящий вебхук с правом CRM для отчётов (Разработчикам → Другое → Входящий вебхук), не тот, что у Ward | alatoo.bitrix24.kz |
| Человек | Telegram: создать бота у @BotFather; создать тестовую группу и группу для отчётов, добавить туда бота | Telegram |
| Человек | Внести секреты (Supabase, Meta, Telegram, ключ шифрования) в переменные окружения Vercel по списку из `.env.example` | Vercel |
| Важно | Токены не передаются агенту в чате и не попадают в репозиторий. Ключи интеграций вносятся через формы кабинета и хранятся зашифрованными | — |

**Готово, когда:**

- [ ] Репозиторий, проекты Supabase и Vercel созданы, у агента есть доступ к репозиторию.
- [ ] Приложение Meta и доступ к рекламному аккаунту готовы, вебхук Bitrix24 и бот Telegram созданы.
- [ ] Просьбы отправлены в поддержку Ward.

## Этап 2 — интеграции и синхронизация

Результат этапа — данные Meta, Ward и Bitrix24 сами попадают в базу по расписанию и сходятся с кабинетами источников.

### Общее

| Метка | Задача |
| --- | --- |
| ИИ | Общий интерфейс адаптера: `testConnection()`, `sync(period)`, `normalize(raw)`. Каждый ответ пишется в `raw_payloads`, каждый запуск — в `sync_runs` |
| ИИ | Очередь задач на `pgmq` и эндпоинт `POST /jobs/tick` с секретом, который вызывает Supabase Cron. Задачи делятся на порции «источник × день», повторяются с паузой, два запуска одной задачи не идут одновременно |
| Важно | Синхронизация идемпотентна: повтор за тот же период обновляет записи (upsert по id источника), а не создаёт дубли |
| Изучить | Лимит длительности функции на тарифе Vercel → размер порции и частота `tick` |

### Meta Ads

| Метка | Задача |

| ИИ | Статистика по объявлениям по дням: расход, показы, клики, `actions`. Последние 7 дней — несколько раз в день, последние 28 — раз в сутки, при подключении — история за 90 дней |
| Важно | Лиды Meta берутся из `actions` по типу, выбранному для цели кампании (например, `onsite_conversion.messaging_conversation_started_7d` или `onsite_conversion.lead_grouped`). `actions` хранится целиком, чтобы метрику можно было сменить без перезагрузки |

### Ward

| Метка | Задача |
| --- | --- |

| Важно | `from`/`to` — даты в UTC. Дни по Бишкеку считаем сами по `created_at`, запрашивая период на день шире; готовую разбивку `daily` не используем |

- [ ] Повторная синхронизация не создаёт дублей.
- [ ] Ошибка источника видна в карточке и журнале, а не теряется молча.

## Этап 3 — сверка и метрики

Результат этапа — единый журнал лидов и метрики по дням, где любое число раскрывается до конкретных записей. Формулы — из раздела «Правила подсчёта» описания проекта.

| Метка | Задача |
| --- | --- |
| ИИ | Модуль `reconciliation` строит `leads` из `ward_leads` и `b24_deals`: связка по `crm.id`; канал — реклама (есть объявление), органика (пост без рекламы), «Direct, источник не определён», другой канал (сделки Bitrix24 без лида Ward) |
| ИИ | Дубли: тот же Instagram или телефон в окне 30 дней (окно — в настройках) → повторное обращение, а не новый лид |
| ИИ | Флаги: лид без сделки (пустой `crm_id` или ошибка Ward — сейчас таких 7), сделка с рекламной меткой без лида, объявление из неподключённого кабинета, лид без телефона |
| Важно | Сверка не меняет таблицы источников и не подгоняет числа. Ручные решения — только через `lead_overrides` с автором и причиной |
| ИИ | `metrics_daily` пересчитывается за изменившиеся дни после каждой синхронизации; дни — по Asia/Bishkek |
| ИИ | Формулы в `packages/shared`: расход; лиды с рекламы (факт и Meta); органика; Direct без источника; другие каналы; цена за лид факт и Meta (расход ÷ рекламные лиды, органика не входит); с телефоном; продажи |
| Важно | Источник отстал или вернул ошибку → значение «нет данных с …», а не ноль. Последние 7 дней помечены как предварительные |
| ИИ | Курсы в `fx_rates` по дням; сомы везде показываются мелко и со знаком ≈ |
| Изучить | Источник курса доллара к сому (Нацбанк КР или другой) и как получать его автоматически |
| ИИ | API для экранов: сводка, ряды по дням, креативы, лиды с фильтрами; у каждой метрики — запрос «из чего сложилось» |

**Готово, когда:**

- [ ] Тесты формул и сверки на записанных ответах API проходят, включая лиды на стыке суток (UTC против Бишкека).
- [ ] Для любой цифры запрос «из чего сложилось» возвращает записи, которые в сумме дают ровно её.
- [ ] Лиды, не дошедшие до Bitrix24, видны с флагом.

## Этап 4 — экраны кабинета

Результат этапа — маркетолог и владелец бизнеса видят все цифры в кабинете. Макет и блоки экранов — в описании проекта.

| Метка | Задача |
| --- | --- |
| ИИ | «Обзор»: полоса «Сегодня · Неделя · Месяц» (неделя — с понедельника, месяц — с 1-го числа), ключевые цифры с изменением к прошлому периоду, лиды по дням (реклама, органика, Direct без источника) и под ними мини-график цены за лид, воронка Ward → Bitrix24, пять лучших креативов, блок «Состояние данных» |
| Важно | Валюта: главная сумма — в валюте кабинета Meta, под ней мелко «≈ N сом» |
| ИИ | «Креативы»: таблица (превью, название, кампания › группа, расход, заявки и цена заявки — факт и Meta, продажи; скрытые колонки — с телефоном, показы, клики, CTR), группировка по объявлениям или кампаниям, вид «галерея», боковая панель с графиком и лидами |
| ИИ | «Лиды»: журнал с фильтрами (источник, креатив, статус, есть ли телефон), карточка с хронологией «объявление → Ward → сделка», экспорт в CSV и Excel |
| Важно | Телефоны и имена клиентов не попадают в логи, Sentry и отчёты в мессенджер; Наблюдатель видит телефоны в маске |
| ИИ | «Настройки»: компания (название, логотип, часовой пояс), правила подсчёта (окно дублей, главная цифра — факт или Meta, метрика Meta для цели кампании), команда и роли |
| ИИ | У каждой цифры — подсказка с формулой и источником; клик открывает список записей, из которых она сложилась |
| Изучить | Блоки «Когда пишут» (день недели × час) и «Что спрашивают» (ЖК, комнаты, бюджет из анкеты Ward): в первую версию, если успеваем, иначе после запуска |
| Человек | Маркетолог проходит все экраны на реальных данных и пишет замечания в PR этапа |

**Готово, когда:**

- [ ] Экраны работают на реальных данных, на телефоне и в тёмной теме.
- [ ] Итоги таблицы «Креативы» за период равны расходу и рекламным лидам на «Обзоре».
- [ ] Сквозной тест Playwright: вход → «Обзор» → клик по цифре → список лидов.

## Этап 5 — отчёты и Telegram

Результат этапа — отчёты сами приходят в группы Telegram по расписанию картинкой с подписью. Макет картинки и шаблон подписи — в описании проекта.

| Метка | Задача |
| --- | --- |
| ИИ | Модель отчёта: шаблон + блоки + фильтры + расписание + получатели. Шаблоны: «Итоги дня» (09:00, за вчера), «Пульс дня» (13:00 и 18:00, за сегодня), «Неделя» (понедельник 10:00), «Месяц» (1-го числа 10:00), «Свой» |
| ИИ | Планировщик: каждую минуту `tick` находит отчёты, у которых наступило время, и ставит отправку в очередь; один и тот же запуск не уходит дважды |
| Важно | Время отчёта хранится в часовом поясе компании и переводится кодом; расписания Supabase Cron считаются в UTC, поэтому в cron только частота `tick`, а не время отчётов |
| ИИ | Картинка: маршрут `/api/og/report/[runId]` в web рисует PNG (шапка, четыре цифры, креативы с превью, подвал с источниками и временем данных) из снимка цифр запуска; файл сохраняется в Storage |
| ИИ | Отправка: `sendPhoto` с подписью до 1024 символов по шаблону из описания; длинный текст — отдельным сообщением; статус доставки — в `report_runs` |
| Важно | Если данные ещё не обновились, отчёт ждёт до 15 минут, потом уходит с пометкой «данные Meta на ЧЧ:ММ». Нули вместо «нет данных» не отправляются никогда |
| ИИ | Telegram: вебхук grammY в api; при добавлении бота в группу она появляется в списке получателей; можно выбрать тему группы |
| ИИ | Экран «Отчёты»: список, конструктор в четыре шага (что, когда, куда, проверка), «Отправить тест мне», история отправок с картинкой того, что ушло |
| ИИ | Алерт: интеграция в статусе «Ошибка» или «Нужно переподключить» → сообщение в группу алертов |
| Человек | Добавить бота в рабочую группу, создать первые отчёты, проверить картинку на телефоне |

**Готово, когда:**

- [ ] «Итоги дня» три дня подряд приходят в тестовую группу вовремя.
- [ ] Цифры на картинке совпадают с кабинетом за тот же период.
- [ ] Отключение интеграции даёт алерт, а отчёт уходит с пометкой, а не с нулями.

## Этап 6 — проверка и запуск

Кабинет считается готовым, когда 14 дней подряд сходится с ручной сверкой маркетолога. Это и есть главная проверка «без вранья».

| Метка | Задача |
| --- | --- |
| Человек | Маркетолог 14 дней параллельно ведёт ручную сверку: расход и лиды по источникам за каждый день |
| ИИ | Каждый день сравнивает ручную сверку с кабинетом. Ошибка кода — исправление с тестом; особенность источника — запись в `docs/decisions/` и подсказка в интерфейсе |
| Важно | Запуск — только когда 14 дней подряд нет необъяснённых расхождений |
| ИИ | Продакшен: переменные окружения prod, Sentry, проверка резервных копий Supabase, контроль расписания: если `tick` не вызывался дольше 10 минут — алерт |
| Человек | Подключить домен, перевести отчёты из тестовой группы в рабочую, пригласить владельца бизнеса |
| Изучить | Хватает ли встроенных резервных копий на тарифе Supabase |

**Готово, когда:**

- [ ] 14 дней подряд цифры сходятся с ручной сверкой или расхождение объяснено.
- [ ] Отчёты уходят в рабочую группу, владелец бизнеса заходит и смотрит метрики сам.
