# 0012 — Срок хранения служебных таблиц

23.11.2026. Синхронизация пишет каждый ответ внешнего API в `raw_payloads`, каждый запуск — в
`sync_runs`, pg_cron — каждый вызов `tick` в `cron.job_run_details`. Удаления не было нигде.
Замер на Ala-too (16–22.11): `raw_payloads` — 49 МБ из 83 МБ базы, +7,3 МБ в сутки на крупную
компанию (56% — ответы WARD `/conversations`, опрос каждые 15 минут). На 150 компаниях — ~16 ГБ в
месяц при 8 ГБ диска Supabase Pro; диск Supabase растёт сам, но обратно не уменьшается.

## Решение

| Таблица                | Хранить | Почему                                                           |
| ---------------------- | ------- | ---------------------------------------------------------------- |
| `raw_payloads`         | 14 дней | отладка свежих расхождений; данные уже разложены по таблицам     |
| `sync_runs`            | 30 дней | «Журнал запусков» на «Интеграциях» показывает последние 50       |
| `cron.job_run_details` | 7 дней  | только для проверки, что `tick` вызывается (`supabase/cron.sql`) |

- **Что читается после срока — не удаляется.** Из `raw_payloads` код читает только последний
  ответ `crm.status.list` (названия источников Bitrix24, `MetricsRepository.bitrixSources`).
  Последний ответ по каждому подключению из списка `RAW_KEEP_LATEST` остаётся, сколько бы ему ни
  было. Новый код, который читает `raw_payloads`, добавляет свой endpoint в этот список.
- **Где запускать — внутри `tick`, раз в сутки** (`jobs/retention.ts`), как курс НБКР
  (`fx.ensureToday`). Не pg_cron: очистка живёт в коде и проходит через PR и тесты, владельцу не
  нужно ничего запускать в SQL Editor, и она не может «потеряться» при переносе проекта.
  Отметка о запуске — строка `retention` в `heartbeats`: захват атомарный, из параллельных `tick`
  чистит один. Раз в 23 часа, чтобы время запуска не уползало.
- **Порциями по 5 000 строк** — короткие DELETE без долгих блокировок. На очистку — не больше
  20 секунд вызова `tick`, остальное — очереди. Не успели — отметка снимается, следующий `tick`
  продолжит. Для выбора строк — индексы по `raw_payloads.fetched_at` и `sync_runs.started_at`
  (миграция 0014).
- `cron.job_run_details` чистит api теми же правами, что и всё остальное (роль `postgres`). Нет
  схемы `cron` (локальная база) или прав — предупреждение в логе, остальная очистка идёт.
- Место после DELETE Postgres не отдаёт диску, а переиспользует (autovacuum): таблица
  перестаёт расти и держится на уровне «14 дней данных». Сжимать файлы (`VACUUM FULL`) не нужно.
