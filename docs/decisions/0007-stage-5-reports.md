# 0007 — Отчёты в Telegram (Этап 5)

## Картинка: next/og

- `ImageResponse` в web (`/api/og/report/[runId]`) — flexbox и подмножество CSS (Satori), шрифты только
  `ttf/otf/woff`, бандл до 500 КБ.
- Кириллица — `@fontsource/inter` (npm): `inter-{cyrillic,latin}-{400,700}-normal.woff`, 88 КБ, читаются файлом.
- Превью креативов — копии в Supabase Storage (Этап 2); пока Meta не подключена — заглушка.
- Картинку рисует web по **снимку цифр запуска**: web получает снимок у api по подписанной ссылке
  (HMAC от `CRON_SECRET`, срок 10 минут) — web не хранит секретов, а цифры на картинке и в подписи одни.

## Telegram: тонкий клиент на fetch, без grammY

Нужны 4 метода Bot API (`sendPhoto`, `sendMessage`, `setWebhook`, `getMe`) и разбор двух видов обновлений
(`my_chat_member`, `message`). Свой клиент на fetch + zod проще и не тянет зависимость, у которой своя
модель бота и middleware. Вебхук: `POST /telegram/webhook` с `X-Telegram-Bot-Api-Secret-Token`
(производный от `CRON_SECRET`).

## Привязка групп к компании — кодом

Бот один на сервис, а компаний будет много (SaaS). Чтобы чужая компания не увидела вашу группу, группа
привязывается командой `/connect <код>` из экрана «Отчёты»; код — у каждой компании свой. Команда, отправленная
внутри темы форума, запоминает тему как получателя.

## Расписание

- Время отчёта хранится в поясе компании (`09:00`), переводится кодом; cron только будит `tick`.
- Слот запуска — `(отчёт, время слота)`, уникален в `report_runs`: один слот не уходит дважды.
- Данные свежие, если источник синхронизировался после «слот − интервал источника» (Ward 20 мин, Bitrix24
  70 мин, Meta 3 ч 10 мин). Не свежие — ждём до 15 минут, затем отправляем с пометкой
  «данные Ward на ЧЧ:ММ». Нули вместо «нет данных» не отправляются никогда.
