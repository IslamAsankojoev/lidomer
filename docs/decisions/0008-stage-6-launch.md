ТЗ, Этап 6: продакшен (переменные окружения, Sentry, резервные копии, контроль расписания) и 14 дней
ручной сверки. Раздел «Что изучить»: хватает ли встроенных резервных копий Supabase.

## Резервные копии Supabase

По документации Supabase ежедневные копии делаются только для проектов **Pro, Team и Enterprise**.
Pro хранит последние **7 дней**, восстановление — в панели (Database → Backups). Для Free копии не
описаны; Supabase советует самим выгружать базу `supabase db dump` и хранить копию вне Supabase.
Восстановление на любую секунду (PITR) — платное дополнение.

Что в базе невосполнимо, а что нет:

- **Восполнимо:** лиды, сделки, расход, сырые ответы — заново выгружаются из Ward, Bitrix24 и Meta
  (история источников длиннее недели).
- **Невосполнимо, но мало:** компании, участники и роли, настройки подсчёта, разметка стадий, отчёты,
  получатели, история отправок.

**Решение:** к запуску проект Supabase — на **Pro** (ежедневные копии за 7 дней). PITR не нужен:
потеря суток невосполнимых данных — это несколько правок настроек, а данные источников перевыгружаются.
Свою выгрузку базы в GitHub или другое хранилище **не делаем**: в ней телефоны и имена клиентов, а им
нельзя покидать базу (AGENTS.md).

Пока проект на Free, копий нет — это риск, который владелец принимает до перехода на Pro.

## Контроль расписания: сторож на GitHub Actions

Расписание — Supabase Cron раз в минуту вызывает `POST /jobs/tick`. Нужно знать, если `tick` не
вызывался дольше 10 минут: cron отключён, сменился секрет, api не отвечает.

- Каждый `tick` записывает пульс в таблицу `heartbeats` (справочная, без `workspace_id`).
- `GET /jobs/watchdog` (тот же `CRON_SECRET`) проверяет пульс. Пульс старше 10 минут — один алерт в
  группы алертов всех компаний; пульс снова свежий — одно сообщение «восстановлено». Повторно не шлёт.
- Вызывает сторожа **GitHub Actions** по расписанию раз в 10 минут. Он не зависит ни от Supabase, ни
  от Vercel: если api вообще не отвечает, запуск workflow падает и GitHub пишет владельцу на почту.

Почему не Vercel Cron: команда Vercel сейчас на **Hobby**, там cron — раз в сутки (на Pro — раз в
минуту). После перехода на Pro сторожа можно перенести в Vercel Cron, но GitHub Actions останется
независимее. Расписание GitHub бывает с задержкой в несколько минут — для порога 10 минут это допустимо.

## Sentry

- api — `@sentry/nestjs`, web — `@sentry/nextjs`. Без `SENTRY_DSN` / `NEXT_PUBLIC_SENTRY_DSN` Sentry
  выключен: локально и в тестах ничего не уходит.
- Телефоны и имена клиентов не попадают в Sentry: `sendDefaultPii: false`, а `beforeSend` вырезает
  тела запросов и ответов, query-строки, cookies и заголовки авторизации, и маскирует телефоны в тексте
  ошибок. Повтор сессий (Replay) не включаем — он записывает экран со списком лидов.
- Регион данных Sentry — EU (проект создаёт владелец).
- Версия SDK — 11.10.0 (старше двух недель на момент подключения). Sentry тянет `@opentelemetry/api`,
  и pnpm разводил `drizzle-orm` на две копии с несовместимыми типами; `@opentelemetry/api` добавлен в
  `packages/db`, чтобы копия была одна.

## Продакшен

- Сейчас один проект Supabase (eu-west-1) обслуживает и кабинет, и проверки: тесты с `RUN_DB_TESTS=1`
  создают временные компании в той же базе. Для запуска это допустимо, только если такие тесты больше не
  запускаются против неё. Отдельный prod-проект по решению 0001 остаётся рекомендацией: владелец решает,
  создавать ли его до запуска (тогда — миграции, Cron, Storage, переменные Vercel, переподключение
  интеграций).
- Vercel — на **Pro** до запуска (решение 0001: Hobby только для некоммерческого использования).

## 14 дней ручной сверки

Маркетолог каждый день заполняет таблицу по шаблону `docs/setup/sverka-template.csv` (день, расход Meta,
лиды по каналам). Скрипт `pnpm --filter @lidomer/api sverka <файл.csv>` сравнивает её с кабинетом за те же
дни и печатает расхождения. Каждое расхождение — либо исправление кода с тестом, либо запись сюда же,
в `docs/decisions/`, с подсказкой в интерфейсе.

Пока Meta Ads не подключена, расход не сверяется — 14 дней без Meta закрывают только лиды.
