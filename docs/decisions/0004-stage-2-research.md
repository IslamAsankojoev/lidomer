# 0004 — Вопросы «Изучить» перед Этапом 2

Проверено 16.11.2026. Решение по каждому пункту принимает владелец; ниже — вывод агента.

## 1. Версия Graph / Marketing API

- Актуальная версия — **v27.0** (вышла 4 ноября 2026). v26.0 — 29 июля 2026, v25.0 истекает 23 февраля 2027.
- У Marketing API вызов истёкшей версии **падает с ошибкой**, а не переходит на соседнюю версию.

**Решение:** версия — одна константа в клиенте Meta (`v27.0`). Карточка интеграции показывает ошибку версии как
«Нужно обновление», а не как «нет данных». Обновлять версию раз в полгода.

## 2. Лимиты Insights

- Лимиты Marketing API считаются отдельно от Graph API, по рекламному аккаунту и бизнесу. Текущий
  расход видно в заголовках ответа: `X-Business-Use-Case-Usage`, `X-Ad-Account-Usage`, `X-FB-Ads-Insights-Throttle`.
- При превышении приходят ошибки 17, 613, 80000 (Insights) — нужен откат с паузой.
- Точные формулы известны только из сторонних статей и расходятся между собой — на них не опираемся.

**Решение:** клиент читает заголовки и замедляется, когда использование > 75%. На ошибках лимита
задача уходит в очередь с паузой, а не повторяется сразу. Запрос — `level=ad`, `time_increment=1`,
поля `spend, impressions, clicks, actions`; длинные периоды (история за 90 дней) — по 7 дней.

## 3. Уровень доступа и проверка приложения

- Для **своего** рекламного аккаунта достаточно Standard Access: приложение и системный пользователь
  принадлежат тому же бизнес-портфолио, что и рекламный аккаунт. Проверка приложения (App Review) не нужна.
- Standard Access даёт заметно меньшие лимиты — для одного аккаунта этого хватает.
- Для **чужих** аккаунтов (SaaS, версия 3) нужны Advanced Access к `ads_read`, App Review и
  проверка бизнеса (Business Verification).

**Решение:** на Этапе 2 — Standard Access. Advanced Access и проверку — в ТЗ версии 3.

## 4. Какой «результат» Meta у кампаний с комментариями

Документация ответа не даёт: тип результата зависит от цели кампании и места конверсии. Это
проверяется только на реальных данных.

**Решение:** `actions` храним целиком (как и требует ТЗ). После подключения Meta агент выгрузит
список типов `action_type` по каждой кампании за 30 дней и принесёт таблицу «кампания → цель →
типы действий», а маркетолог выберет метрику лида для каждой цели в «Настройках».

## 5. Метод списка сделок Bitrix24

- `crm.deal.list` и `crm.item.list` помечены «Развитие метода остановлено. Используйте метод REST 3.0».
- REST 3.0 вызывается тем же входящим вебхуком, но через `/rest/api/`:
  `https://alatoo.bitrix24.kz/rest/api/{user_id}/{код_вебхука}/crm.deal.list` — только POST с JSON.
- Фильтр: массив условий `["field", "operator", value]`, операторы `= != > >= < <= in between`.
  Сделки, направления и стадии в REST 3.0 есть.
- Формат постраничной выборки в обзоре не описан — схему даёт метод `rest.documentation.openapi`.

**Решение:** клиент Bitrix24 — на REST 3.0 (`crm.deal.list`, стадии через `crm.category.*`/стадии
REST 3.0). Синхронизация — по `updatedTime >= последний запуск`, ночная полная — по `id >` (keyset).
Первым шагом Этапа 2 агент вызывает `rest.documentation.openapi` на портале и фиксирует схему
пагинации в тестах. Если REST 3.0 на портале недоступен — запасной путь `crm.deal.list` v2
с keyset по `ID`.

**Поправка (Этап 2, 17.11.2026):** документация REST 3.0 не подтверждает имена нужных полей сделки
(валюта, источник, UTM, даты изменения и закрытия), а сверить их на портале пока нельзя — вебхука нет.
Поэтому клиент сделан на `crm.deal.list` v2: поля документированы, метод работает, «развитие остановлено»
не значит «отключён». Выборка — по `ID` возрастанию с `start=-1` (без подсчёта total), изменённые — по
`>=DATE_MODIFY`. Переход на REST 3.0 — отдельной задачей после `crm.deal.field.list` на портале.
