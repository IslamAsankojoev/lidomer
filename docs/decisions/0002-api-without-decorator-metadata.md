# 0002 — api без emitDecoratorMetadata, проверка входа через ZodPipe

## Контекст

NestJS обычно определяет зависимости и DTO по метаданным типов (`emitDecoratorMetadata`).
Их выдаёт только компилятор `tsc`; esbuild/oxc (Vitest, сборщики Vercel) их не выдают. Пакет
`nestjs-zod` из ТЗ строит проверку на тех же метаданных и пока поддерживает только Nest 10–11.

## Решение

- Все зависимости внедряются явно: `constructor(@Inject(Token) x: X)`.
- Входные данные проверяются явно: `@Body(new ZodPipe(schema))`, схемы — из `packages/shared`.
- `nestjs-zod` и `@nestjs/config` не используем: окружение проверяет zod-схема в `config/env.ts`,
  результат доступен как провайдер `ENV`.
- NestJS 11 (не 12): под него есть совместимые версии экосистемы; TypeScript 5.9.

## Последствия

- Код одинаково работает после `tsc`, в Vitest и в сборке Vercel — без SWC-плагинов.
- Забытый `@Inject` даст ошибку при старте, а не молчаливое `undefined`: e2e-тест поднимает весь `AppModule`.

## Поправка (17.11.2026): tsconfig api без extends

Сборщик NestJS на Vercel проверяет типы своим компилятором и **не читает унаследованный tsconfig**
(`extends` — ни через пакет, ни относительным путём). Без `strict` zod-типы `nullable()` выводятся иначе,
и деплой падал, хотя локальный `tsc` и CI были зелёными. Поэтому `apps/api/tsconfig.json` задаёт все
опции явно: локальная проверка и сборка Vercel видят одно и то же.
